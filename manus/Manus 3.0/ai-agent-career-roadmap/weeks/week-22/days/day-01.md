## 岗位价值

简历、GitHub 与 Demo 对真实 Agent 开发的价值在于：团队需要的不只是一个能演示的模型调用，而是能说明输入、输出、失败路径和责任边界的功能。设计背景可帮助你把用户目标和交互证据说清楚，但必须用代码、测试和日志证明方案可交付。

## 今日学习内容

阅读并复现一个最小可运行示例，记录关键术语。 对设计师而言，可以把工程功能理解为一个具有状态、输入规范、异常状态和验收条件的交互组件；代码就是让这个组件在不同情境下稳定工作的规则集合。英文缩写首次出现时请在笔记中写出全称，例如 API（Application Programming Interface，应用程序编程接口）。

## 编码任务

在对应项目的 `src/` 中新增一个小而可测试的模块，围绕“STAR、项目量化、录屏流程”实现一个明确输入输出。不要复制完整参考实现；先写测试、再完成最小实现。

创建或修改文件时，先在项目 README 的“本周实验”小节列出文件目的。明确写出函数的输入类型、输出类型和错误行为。运行命令以项目 README 为准；成功标准是测试通过、手工样例符合预期、错误输入被可理解地处理。

## 独立完成部分

你必须独立完成：函数签名、至少一个边界测试、错误消息文本，以及对实现取舍的简短说明。不要查看 `reference-solution/`；该目录仅在你明确要求“生成参考实现”后才会包含完整答案。

## 验收标准

- [ ] 功能可以运行。
- [ ] 输入输出符合要求。
- [ ] 错误输入被正确处理。
- [ ] 密钥没有写进代码。
- [ ] README 已更新。
- [ ] 学习记录已完成。

## 常见错误

| 现象 | 优先排查方向 |
|---|---|
| 代码能运行但测试失败 | 检查函数输入边界、类型和断言是否一致。 |
| 环境变量未生效 | 检查 `.env` 是否被 Git 忽略、变量名是否与配置一致。 |
| 模型或外部调用结果不稳定 | 先记录输入、输出、超时和重试；不要用“模型不稳定”代替分析。 |
| 文档与实现不一致 | 更新 README 命令和示例，并重新执行一次。 |
