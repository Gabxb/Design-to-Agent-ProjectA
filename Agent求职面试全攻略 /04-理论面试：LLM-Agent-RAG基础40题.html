LLM 基础

Q1【初级】Transformer 的核心是什么？

注意力机制。一句话：让模型在处理每个 token 时都能"看到"序列中的所有其他 token，计算它们之间的关联权重。

code 
传统 RNN：逐词处理，前面忘后面
Transformer：一次性看全句，每个词和其他词的关系都算出来

Q2【中级】Transformer 的 Q、K、V 是什么？

code 
Q (Query)：  "我在找什么？"（当前词想查什么）
K (Key)：    "我是什么？"（每个词的索引标签）
V (Value)：  "我的内容"（每个词的实际信息）

Attention(Q,K,V) = softmax(QK^T / √d_k) × V

简单理解：用 Q 去和所有 K 算相似度 → 加权平均对应的 V

Q3【初级】什么是 Token？为什么大模型按 Token 计费？

Token 是 LLM 处理的最小文本单元。英文大约 1 词 ≈ 1.3 token，中文大约 1 字 ≈ 2 token。

按 Token 计费的原因：模型的计算量正比于 Token 数（不是字数）。

Q4【中级】什么是 Temperature？Agent 场景怎么设？

code 
Temperature = 0：完全确定性，每次输出一样 → Agent 任务执行 ❗
Temperature = 0.7：有一定随机性 → 创意写作
Temperature > 1：越来越乱 → 不推荐

Agent 建议：任务执行用 0，需要变通用 0.3-0.5

Q5【中级】MoE (Mixture of Experts) 是什么？

不是所有参数都参与每次推理。模型分成多个"专家"子网络，每次输入只激活其中一部分。

code 
传统 Dense：671B 参数全部参与推理
MoE：671B 总参数，但每次只激活 37B

好处：推理快、成本低（DeepSeek-V3 就是 MoE）

Q6【高级】为什么深度 LLM 会出现幻觉？怎么缓解？

根因：模型本质是"下一个 Token 预测器"，不是知识库。它在做概率最优化，不是在"思考是否正确"。

缓解：

  • RAG：把事实喂给 LLM，而不是让 LLM 自己"回忆"
  • 约束输出格式：让 LLM 输出结构化的 JSON，减少自由发挥
  • 事实校验：用第二次 LLM 调用来验证第一次的输出
  • 低 Temperature：减少随机性

Agent 核心

Q7【初级】Agent 和 Chatbot 的本质区别？

code 
Chatbot：你问 → 它答 → 结束
Agent：  你问 → 它想 → 它动手（调工具）→ 它看结果 → 再想 → 循环直到完成

核心差异：工具使用能力 和 自主多步推理。

Q8【中级】ReAct 模式的核心思想？

code 
ReAct = Reasoning + Acting（推理 + 行动）

每一轮：
1. Thought：当前该怎么办？（推理）
2. Action：调用什么工具？什么参数？（行动）
3. Observation：工具返回了什么？（观察）
4. 循环，直到产生 Final Answer

这是当前所有 Agent 框架的基础模式。

Q9【中级】Plan-Execute vs ReAct，什么时候选哪个？

code 
ReAct：走一步看一步
  适合：任务路径不明确、需要灵活应变
  缺点：可能绕远路

Plan-Execute：先规划全图，再逐步执行
  适合：任务可预先拆解、步骤多
  缺点：如果计划错了，纠正成本高

选择：简单任务用 ReAct，复杂多步任务用 Plan-Execute

Q10【中级】Function Calling 的原理是什么？

code 
1. 开发者定义工具的 JSON Schema（名称、描述、参数格式）
2. 把 Schema 放在 API 请求的 tools 参数中
3. LLM 在需要时输出一个 tool_call（而不是文本回复）
4. 开发者收到 tool_call，执行对应的函数
5. 把执行结果返回给 LLM
6. LLM 根据结果继续推理

关键：LLM 不是真的"执行"工具，它只是"输出一个结构化的呼叫请求"

Q11【高级】Agent 为什么会死循环？怎么避免？

原因：

  • LLM 在两个工具之间来回跳（A→B→A→B）
  • 工具返回数据格式不对，LLM 一直重试
  • 任务本身就无解，LLM 不停尝试

解决：

python 
max_iterations = 10  # 硬限制
# 在循环中检查：
if current_action == last_action and same_params:
    return "检测到循环，强制终止"

Q12【中级】Agent 的三种记忆有什么区别？

code 
工作记忆：当前对话的上下文（System Prompt + Message History）
  → 对话越长，Token 消耗越大

短期记忆：会话间的上下文（本次对话和上次的关联）
  → 最简单的方案：每次新对话把上次摘要放进去

长期记忆：跨所有对话的知识（向量库存储 + 检索）
  → FAISS/Milvus 存储 → 检索 → 拼入当前消息

Q13【高级】多 Agent 系统中怎么避免"喊话死锁"？

code 
死锁场景：Agent A 等 B 的结果，B 等 A 的信息，互相等

解决：
1. 超时机制：每个 Agent 调用有 timeout
2. 优先级队列：某个 Agent 有最终决策权
3. 仲裁 Agent：专门一个 Agent 负责打破僵局
4. 限制通信轮次：A→B→A→B 最多 3 轮

RAG 专项

Q14【初级】RAG 的基本流程是什么？

code 
用户提问 → Embedding（向量化查询）
         → 向量数据库检索 Top-K 相关文档
         → 把文档拼接到 System Prompt 中
         → LLM 基于文档生成回答

Q15【中级】RAG 为什么要做向量检索？不能直接全文搜索吗？

code 
全文搜索：只能匹配精确关键词
  用户问"怎么提速" → 找不到"性能优化"文档 ❌

向量搜索：匹配语义相似度
  用户问"怎么提速" → 能匹配到"性能调优指南" ✅

所以 RAG 用向量，因为它要的是语义相似，不是字符匹配

Q16【中级】RAG 为什么要有 Rerank？

code 
向量检索返回 Top-20 是"最像"的，不一定是"最有用"的。

示例：
查询："如何解决 OOM 问题"
Top-1（向量）："OOM Killer 技术白皮书"（语义最像但太长）
Top-15（向量）"服务器内存不足的 3 个排查步骤"（更实用但排名低）

Rerank 模型重新打分：把 Top-15 排到第一 → 提高回答质量

Q17【高级】如何评估 RAG 的质量？

用 RAGAS 框架，四个指标：

code 
Faithfulness：回答是否忠于上下文（不能瞎编）
Answer Relevancy：回答是否切题
Context Recall：上下文中能否找到 ground_truth 所需信息
Context Precision：检索到的文档中有多少是真正有用的

Q18【高级】多路召回是什么？什么时候需要？

code 
单路召回：只用向量搜索 → 适合语义明确的查询

多路召回：
  向量搜索（语义相似）
  + BM25 关键词搜索（精确匹配）
  + 知识图谱（实体关系）
  → 合并去重 → Rerank 排序

需要多路召回的信号：
- 用户查询包含具体名词（人名、产品名、编号）
- 知识文档结构性强（表格、条款、字段名）

Q19【中级】DeepSeek-V3 和 Qwen-3.5 的核心差异？

code 
DeepSeek-V3：
  MoE 架构（671B 总参数，37B 激活）
  优势：推理能力强，函数调用稳定，成本极低

  Dense 架构（7B/14B 参数）
  优势：开源可本地部署、Function Calling 也不错
  适合：本地部署 Agent、数据敏感场景

Q20【初级】为什么 Agent 开发推荐用 Python 而不是 Java？

code 
1. 生态：LangChain/LangGraph 最成熟的是 Python 版
2. 迭代：Agent 需要快速试错（改 Prompt、调参数），Python 更快
3. 数据：Agent 大量使用 NumPy、FAISS、Pandas
4. 社区：大部分 LLM SDK 优先支持 Python

面试深度剖析与高阶案例（高频加分项）

在高级 Agent 研发岗的面试中，单纯回答理论是不够的。面试官往往会通过“场景题”考察你的工程直觉和填坑经验。以下内容通过真实 Case Study 和心智模型，帮你构建降维打击的面试护城河。

1. 真实 Case Study：金融级 RAG 系统的幻觉治理与准确率优化

业务场景：某头部券商需要一个研报问答 Agent，要求回答准确率从 70% 提升至 95% 以上，绝不能出现数字编造（幻觉）。

面试官提问：“你们 RAG 系统遇到过最严重的幻觉问题是什么？怎么解决的？”

高阶回答话术���拆解： “我们遇到的最严重的问题是**‘事实拼接幻觉’和‘数值幻觉’**。比如研报里说 A 公司营收 100 亿，B 公司净利润 20 亿，模型在回答时可能会说 A 公司净利润 100 亿。

为了将准确率提升到 95% 以上，我们没有单纯依赖 Prompt 调优，而是重构了检索与生成的管线，具体做了四层防御：

  1. 入库层：知识结构的显式化（解析与 Chunking 优化）

    • 痛点：传统按长度切分（Token 切分）会截断表格或段落上下文。
    • 方案：引入 Unstructured 等解析工具进行语义切分（Semantic Chunking）。对于财报中的表格，我们提取为 Markdown 或 HTML 格式，甚至直接将其转化为键值对（Key-Value）单独存储，避免表格丢失行列对齐信息。

  2. 检索层：混合检索 + 意图路由（Query Routing）

    • 痛点：用户查“2023年Q3苹果财报”，纯向量检索可能会找出 2022 年的相关段落。
    • 方案：增加 Query 理解模块。在执行检索前，先用轻量级 LLM 提取实体（Entity）和时间（Time），随后执行：
      • 向量检索：捕获语义相似度。
      • BM25 / 标量过滤：强制要求时间、实体等 Metadata 必须匹配。
    • 这也是业内常说的 Self-Querying Retrieval 模式。

  3. 生成层：严格的引用限制与 Chain-of-Verification (CoVe)

    • 方案：在 Prompt 中强制要求模型必须且只能基于上下文回答，并标明出处（Citation）。例如：“如果上下文中没有提到该数字，请回答‘未提及’”。
    • 引入 CoVe（验证链）：在模型生成初步草稿后，我们增加了一个轻量级的 Verify Agent，让它自己对照上下文检查草稿中的数据是否一致。如果发现冲突，则重新生成。

  4. 兜底层：规则引擎与 NLI（自然语言推理）双重校验

    • 对于极端敏感的场景，我们在输出前增加了一道风控模型（基于 DeBERTa 等轻量 NLI 模型），判断生成答案是否与检索片段构成蕴含（Entailment）关系。如果判断为矛盾（Contradiction），直接触发人工降级策略。”

2. 深度架构讨论：Plan-Execute vs ReAct 的底层博弈

面试官提问：“你们在什么场景下会放弃 ReAct，转而使用 Plan-Execute 甚至固定工作流（State Machine）？”

高阶回答话术与拆解： “ReAct 的核心优势是灵活，但它的致命弱点在于推理成本极高且容易发散。在我们的实践中，我们总结出了一个**‘任务确定性矩阵’**：

  • 场景 A：数据查询分析（如 SQL 生成与执行）
    • 选择：ReAct。因为执行 SQL 可能会报错，需要根据报错信息（Observation）动态修改 SQL（Thought & Action）。这种任务的路径是不可预知的。
  • 场景 B：机票预订 / 复杂的多步审批流
    • 选择：Plan-Execute 或 StateGraph（状态机）。
    • 原因：机票预订的步骤是固定的（查航班 -> 选座 -> 填身份 -> 支付）。如果用 ReAct，LLM 可能会在查完航班后突然去查当地天气，导致主线任务偏离（Drifting）。
    • 架构演进：我们甚至发现，单纯的 Plan-Execute 也不够，最好的方式是 LLM 编排 + 确定性代码执行（LangGraph 的核心思想）。LLM 负责生成一个 JSON 格式的执行图（Plan），然后由 Python 代码严格按照图执行。在每个节点，再由小 Agent 负责具体逻辑。

这种思路体现了工程上的控制反转：不要把系统的控制流（Control Flow）完全交给大模型，大模型只应该做数据流（Data Flow）的处理和节点的决策。”

3. 心智模型：Agent 能力评估三角

在评估一个 Agent 架构是否合理时，可以套用以下“能力评估三角”：

  1. 认知力（Cognition）：
    • 包含：模型参数量、Prompt 复杂度、记忆机制。
    • 决定了 Agent “有多聪明”。
  2. 感知力（Perception）：
    • 包含：工具集（Tools/Plugins）、知识库检索（RAG）、多模态输入。
    • 决定了 Agent “能看到什么”。
  3. 行动力（Action）：
    • 包含：沙盒执行环境、API 鉴权调用、RPA、MCP 协议。
    • 决定了 Agent “能改变什么”。

面试运用：“针对您提到的客服 Agent 经常答非所问的问题，套用 Agent 三角来看，往往不是‘认知力’（大模型不够好）的问题，而是‘感知力’出了问题。比如它能调用的 CRM 接口拿不到最新的订单状态。我会优先排查工具和检索的完备性，而不是急着换模型。”

4. 高阶综合：Agent 常见反模式与避坑指南（Summary Table）

反模式 (Anti-Pattern)现象描述根本原因高阶解决方案 (Best Practice)
Prompt 肥胖症一个 Prompt 几千字，写满了无数的 if-else 规则，模型依然不遵循。LLM 的注意力稀释；把 LLM 当成传统编程语言来用。职责分离（Separation of Concerns）：将巨型 Prompt 拆分为多个小 Agent，采用 Multi-Agent 架构。用代码逻辑（Python）来处理 if-else 路由。

记忆过载历史对话全量喂入，导致延迟飙升，且模型被旧信息干扰，产生幻觉。没有建立层级化的记忆管理系统，过度依赖上下文窗口。三级记忆架构：当前窗口（最近5轮） + 摘要记忆（LLM定期总结压缩） + 长期记忆（向量库检索历史实体）。
过度 Agent 化连计算 "1+1" 或者查询固定配置，都要走一轮大模型的规划和执行。盲目追求 AI 浓度，忽略了系统的确定性和延迟。AI 降级策略（Graceful Degradation）：在 Agent 前面加一层意图识别和缓存（Semantic Cache）。如果是规则明确的请求，直接走传统代码分支。

5. 深度原理：Function Calling 与 MCP 的本质区别在哪？

面试官提问：“你觉得有了 Function Calling，为什么 Anthropic 还要搞 MCP（Model Context Protocol）？”

高阶回答话术与拆解： “Function Calling 解决的是**‘语言转结构化数据’的问题，而 MCP 解决的是‘Agent 系统的架构解耦’**问题。

  1. 从架构层面看（解耦）：
    • 使用传统的 Function Calling，开发者必须把工具逻辑（比如查数据库、调 Github API）和 Agent 的主干代码写在一起（或者在同一个进程中引用）。
    • MCP 是一种客户端-服务端架构。Agent 是 Client，各种数据源是 Server。这意味着我可以让 Agent 跑在我的电脑上，而通过 MCP 标准协议连接部署在内网深处的数据库 MCP Server。
  2. 从标准化层面看（协议）：
    • Function Calling 各家模型格式不同（OpenAI vs Anthropic vs 百度）。
    • MCP 统一定义了 Resources（资源）、Prompts（提示模板）和 Tools（工具）三种能力。它就像是 Agent 时代的 USB-C 接口。
  3. 安全与权限控制：
    • 通过 MCP，管理员可以在 Server 端集中控制读写权限，而不需要在每个 Agent 的代码里写鉴权逻辑，更适合企业级的权限隔离。

总结来说，Function Calling 是 LLM 的一项基础能力，而 MCP 是基于这种能力构建的分布式系统通信协议。”

通过以上补充，你的回答将不仅停留在“知道名词”，而是展现出“踩过坑、搭过架构、做过技术选型”的高级工程师风范。

进阶理论深挖：大厂高频硬核考点全解析

6. 模型底层：Transformer 与 KV Cache 原理揭秘

面试官提问：“你刚才提到 Token 计费，那你知道大模型在生成回复时，首字延迟（TTFT）和后续 Token 生成延迟为什么不一样吗？KV Cache 到底缓存了什么？”

高阶回答话术与拆解： “大模型的推理过程分为两个阶段：Prefill（预填充阶段）和Decode（解码阶段）。

  • Prefill 阶段：模型一次性读取用户输入的全部 Prompt。这是一个计算密集型（Compute-bound）操作，GPU 并行计算所有输入 Token 的 Q（Query）、K（Key）、V（Value）向量。这就导致了首字延迟（TTFT，Time To First Token）。
  • Decode 阶段：模型开始一个一个地吐出新 Token。这时候是内存访存密集型（Memory-bound）操作。

KV Cache 的作用： 在 Decode 阶段，生成第 N 个 Token 需要计算它与前面 N-1 个 Token 的注意力（Attention）。为了避免重复计算前面 N-1 个 Token 的 K 和 V 向量，模型会将它们缓存进显存中，这就是 KV Cache。

  • 为什么只存 KV 不存 Q？：因为计算当前的 Attention 只需要当前的 Q 去和历史所有的 K 算内积，然后再加权历史所有的 V。历史的 Q 已经用过了，不需要再存。
  • 容量危机：在超长上下文（如 128K）场景下，KV Cache 会急剧膨胀，挤占模型权重的显存，导致 OOM。业内通常用 PagedAttention（vLLM 的核心技术）像操作系统管理内存分页一样来管理 KV Cache，极大提升了并发吞吐量。”

7. RAG 高阶检索策略：超越基础向量搜索

面试官提问：“基础的 Embedding 检索效果不好，除了 Rerank，你们还在检索阶段做过哪些进阶优化？”

高阶回答话术与拆解： “基础 RAG 是‘对称检索’（用短 Query 搜长 Document），两者语义空间不对等。为了解决这个问题，我们引入了以下几种高阶检索策略：

  1. HyDE (Hypothetical Document Embeddings)

    • 原理：先让 LLM 根据用户的 Query ‘盲猜’（生成）一篇假文档（Hypothetical Document），然后对这篇假文档做 Embedding，再去向量库中搜索。
    • 优势：将‘对称检索’变成了‘文档到文档’的检索，大大提高了语义命中率。
    • 坑点：会增加一次 LLM 调用的延迟，且如果模型生成的假文档完全跑题，会带偏检索结果。

  2. Parent Document Retriever (父子文档检索)

    • 痛点：Chunk 切得太小，LLM 缺乏上下文；切得太大，向量检索不精准。
    • 方案：在切分文档时，同时保留‘大块（父文档）’和‘小块（子文档）’。把子文档做 Embedding 存入向量库。当检索命中某个子文档时，顺藤摸瓜把它的父文档完整提取出来喂给 LLM。
    • 优势：兼顾了‘检索的高精度’和‘生成的高上下文’。

  3. Multi-Query Retrieval / Query Expansion (多路查询扩展)

    • 机制：用户问‘如何优化 MySQL 查询？’，先让 LLM 把这个问题改写成 3-5 个不同表述的问题（如‘MySQL 慢查询排查步骤’、‘InnoDB 索引优化’）。
    • 然后对这 5 个问题同时执行检索，将结果合并去重（Reciprocal Rank Fusion, RRF）。
    • 适用：用户提问非常口语化或模糊的场景。

8. 复杂推理架构：从 CoT 到 Tree of Thoughts (ToT)

面试官提问：“除了让大模型‘Step by step’思考，遇到极度复杂的逻辑推理任务，有什么高级的 Prompt 架构设计？”

高阶回答话术与拆解： “Chain of Thought (CoT) 只是线性推理，一旦中间某一步算错，后面全错（错误级联）。在解决例如数学难题、复杂代码逻辑生成或深度调研任务时，我们会使用更复杂的规划范式：

  1. Self-Consistency (自我一致性 / 多数投票)

    • 让模型生成 5 条不同的推理路径，最后看哪个答案出现的次数最多（Majority Voting）。这是一种用计算量换准确率的暴力美学。

  2. Tree of Thoughts (ToT, 思维树)

    • 原理：将推理过程抽象为树状搜索（类似下棋算法）。在每一步（每个节点），让 LLM 生成多种可能的下一步（枝桠），然后让 LLM 自己对这些枝桠进行评估打分（Evaluation）。
    • 配合 BFS（广度优先搜索）或 DFS（深度优先搜索）算法，舍弃低分路径，探索高分路径。
    • 应用场景：比如让 Agent 写一篇长篇小说，先生成 3 个不同的大纲，评估选一个最好的；再为这个大纲生成 3 个不同的人物设定，评估再选一个……
    • 代码实现：通常不再是用单一 Prompt，而是通过 Python 代码写一个 While 循环，不断调用大模型做 Generate 和 Evaluate。

  3. Reflexion (反思机制)

    • 机制：Agent 做出行动 -> 环境返回报错（如代码运行失败） -> Agent 分析报错原因（Reflection） -> 将反思经验写入工作记忆 -> 再次尝试。
    • 相比于死磕代码，加入了独立的‘批判反思’步骤，极大提升了 Agent 在沙盒环境中的任务成功率。

9. 模型选型与对比：如何评估 Llama 3、Qwen、DeepSeek 等开源模型？

面试官提问：“如果公司要全面私有化部署大模型，你会如何做技术选型？”

高阶回答话术与拆解： “选型不能光看大厂的榜单，必须结合业务场景的‘长板需求’。我会从以下四个维度构建评估矩阵：

  1. 中文原生支持与文化对齐

    • Qwen (千问) 和 DeepSeek 是国内开源的双壁。它们的中文语料占比高，对国内的政企公文、专有名词、文化语境理解远超 Llama 3。
    • 尤其是处理财报解析、合同比对等任务，首选 Qwen-72B/110B 或 DeepSeek-V3。

  2. 代码与数学推理能力（Agent 的大脑）

    • Agent 要稳定执行工具调用（Function Calling）和 JSON 输出，必须具备极强的代码和逻辑能力。
    • DeepSeek-Coder/V3 在这一领域长期霸榜，甚至在部分 benchmark 上比肩 GPT-4o。如果构建写代码的 Agent 或数据分析 Agent，DeepSeek 是首选。
    • Llama 3 (70B/400B) 逻辑能力极强，但中文需要额外微调，或者用社区的汉化版本。

  3. 架构与硬件成本 (Dense vs MoE)

    • 如果公司只有几张卡（如 2 张 A100），部署 70B 级别的 Dense 模型（如 Llama 3 70B 或 Qwen 72B）是极限。
    • 但如果追求极致的推理速度和高并发，DeepSeek-V3 (MoE架构) 是最优解。虽然总参数量 671B 需要多台机器加载（或者用量化版），但其每次推理激活的参数仅约 37B，推理速度极快，适合大流量的 C 端 Agent 服务。

  4. 工具生态兼容性

    • Qwen 和 DeepSeek 的 API 格式完美兼容 OpenAI 格式。这意味着 LangChain、LangGraph 的底层代码不需要做任何修改，直接把 base_url 改成本地 vLLM 地址即可无缝迁移，迁移成本极低。

10. 高阶心智模型：第一性原理看大语言模型

在面试的最后，常常会探讨对 AI 发展趋势的看法。可以抛出这个心智模型：

将 LLM 视为一种“模糊的操作系统（Fuzzy OS）”：

  • CPU / 内存 = LLM 的推理能力（Context Window 和 Token 生成速度）
  • 硬盘 = RAG 向量数据库（提供持久化存储和长短期记忆）
  • 外设 / 驱动 = 工具集 (Tools) 与 MCP 协议（允许 LLM 操控现实世界）
  • 应用程序 = Agent 工作流（通过 Prompt 和状态机编排出来的任务序列）

基于这个心智模型，我们可以得出结论： 未来的竞争不在于谁能微调出更好的“CPU”，而在于谁能把“外设接入（MCP）”和“应用程序（Agent 编排框架）”做得最稳定、最符合业务逻辑。这就是为什么工程能力在 Agent 时代依然是决定性因素。”

通过掌握这些深入的底层机制（KV Cache、高级 RAG、ToT推理），你将向面试官展示出你不仅能写业务代码，还具备解决底层性能瓶颈、把控架构演进的高级技术专家潜力。

11. 理论深挖：RAG 评估体系 (RAGAS) 与指标拆解

面试官提问：“你提到用 RAGAS 评估，那如果‘回答相关性（Answer Relevancy）’很高，但‘忠实度（Faithfulness）’很低，说明系统出了什么问题？”

高阶回答话术与拆解： “这是一个典型的**‘幻觉’（Hallucination）症状**。

  • Answer Relevancy 高说明 LLM 生成的回答很切题，确实是在回答用户的问题。
  • Faithfulness 低说明回答中的关键事实（实体、数字）无法在检索到的上下文中找到。

根因排查与修复：

  1. 检索出的上下文质量太差：LLM 发现上下文里没有答案，于是依靠自己预训练的内部知识（Internal Knowledge）强行编造了一个回答。
    • 修复：优化检索管线（如引入 Reranker 或 Hybrid Search），提高 Context Precision。
  2. Prompt 约束力不足：大模型没有听从“必须仅基于上下文回答”的指令。
    • 修复：在 Prompt 中加强系统指令，甚至使用 System Prompt 加上 Few-shot 示例，告诉大模型如果上下文中没有该如何回答（如“根据知识库，我无法获取该信息”）。

这种分析展示了你不仅知道指标的名字，更知道如何用指标来指导系统调优。

12. 底层理论：向量空间坍塌 (Vector Space Collapse) 与各向异性

面试官提问：“为什么有时候两个完全无关的句子，算出来的 Cosine Similarity 也有 0.8 以上？怎么解决这种区分度不高的现象？”

高阶回答话术与拆解： “这是自然语言处理领域经典的表征退化（Representation Degeneration）问题，也叫向量的各向异性（Anisotropy）。

  • 原因：在未经过强对比学习（Contrastive Learning）优化的模型中，生成的词向量或句向量往往集中在一个很狭窄的锥形空间内，而不是均匀分布在整个高维空间。这导致任意两个向量的夹角都很小（余弦相似度都很高），失去了区分力。
  • 解决方案：
    1. 换模型：不要用早期的 BERT 或通用 LLM 的最后隐层特征直接当 Embedding。必须使用在检索任务上专门训练过的模型（如 BGE-m3, text-embedding-3）。
    2. 加入对比学习：在微调 Embedding 模型时，使用 InfoNCE Loss，把相似句子的距离拉近（正样本），同时强行把不相关句子的距离拉远（Hard Negatives 难负样本挖掘）。
    3. 白化处理（Whitening）：在工程上，如果无法更换模型，可以通过对向量计算协方差矩阵并进行白化（类似 PCA 降维变换），强行让向量在各个维度上分布更均匀。

13. 多模态 Agent 理论：CLIP 与 ViT 的融合机制

面试官提问：“如果我们要让 Agent 能看懂用户上传的 UI 截图并生成前端代码，底层的多模态模型（如 GPT-4V 或 Qwen-VL）是如何把图片和文字放在一起理解的？”

高阶回答话术与拆解： “多模态理解的核心在于对齐不同模态的特征空间。主流架构通常包含三个组件：

  1. 视觉编码器（Visual Encoder）：通常是 ViT（Vision Transformer）或者 CLIP 的视觉分支。它把一张高分辨率图片切分成许多小块（Patches），把每个小块变成一个向量。
  2. 适配层（Adapter / Projector）：这是最关键的桥梁。因为图像向量的维度和文本大模型的维度不同，通常会用几层 MLP 或 Q-Former 网络，把图像向量映射到大语言模型的文本输入空间中。
  3. 大语言模型（LLM Backend）：经过映射后，一张图片在 LLM 看来，就像是几百个特殊的“图像单词（Image Tokens）”。LLM 把这些图像单词和用户输入的文字 Prompt 拼接在一起，统一用 Transformer 里的 Self-Attention 机制去计算它们之间的关系。

面试运用：“所以当 Agent 看不懂截图上的小字时，往往是因为图片在 ViT 阶段被缩放压缩了，或者是 Patch 分得不够细。在架构上，如果图片文字密集，我会优先前置一个 OCR 引擎把文字抠出来，以文本形式补充进 Prompt，而不是单纯指望视觉编码器。”

14. 心智模型：LLM 系统的认知层次模型 (The LLM Capability Hierarchy)

面试官经常会考察你的认知高度。你可以用这个层次模型来阐述 AI 系统的演进：

  1. Level 1: 文本操纵者 (Text Manipulator)
    • 核心能力：翻译、润色、摘要、代码补全。
    • 典型代表：早期的 ChatGPT 网页版，GitHub Copilot。系统是被动的，只有文本进，文本出。
  2. Level 2: 工具使用者 (Tool User)
    • 核心能力：Function Calling，RAG。
    • 典型代表：具有联网能力的问答系统。LLM 开始可以“感知”外部世界（读取天气、查数据库）。
  3. Level 3: 自主代理 (Autonomous Agent)
    • 核心能力：多步规划（Planning），自我纠错（Reflexion），状态维持。
    • 典型代表：AutoGPT，Devin。大模型不仅能调用一次工具，还能根据工具的返回结果，独立决定下一步该怎么走，直到完成复杂目标。
  4. Level 4: 多智能体社会 (Multi-Agent Society)
    • 核心能力：社会化分工，动态协议，仲裁。
    • 系统中不再只有一个全能的“上帝”模型，而是由成本低、响应快、具备不同人设的微型 Agent 组成复杂的数字流水线。

战略建议：“目前很多企业在落地时，试图一步到位跨入 Level 3，导致失败率极高。我们的工程实践是：先做稳 Level 2（把工具库和 RAG 做到 99% 的可靠度），然后逐步引入有限度的 Level 3 自动化。”

15. 真实 Case Study：为什么大模型数学很差？Code Interpreter 是怎么救场的？

业务场景：面试官问：“你们用大模型做财务报表分析时，为什么大模型算 3456.78 * 89.12 总是算错？怎么彻底解决大模型数学计算拉垮的问题？”

高阶回答话术与拆解： “大模型算错数学题是其底层架构决定的。由于 Tokenizer 的机制，数字在分词时会被切得支离破碎（比如 3456 可能被切成 [34, 56] 或 [3, 456]）。大模型在预测下一个 Token 时，它是在做‘语言概率接龙’，而不是在使用 CPU 的 ALU（算术逻辑单元）做精确的二进制乘法。因此，纯靠大模型算数学题，本质上是在‘背诵九九乘法表’，位数一多必然出错。

彻底解决的架构方案：引入 Code Interpreter（代码解释器）模式。

  • 我们完全剥夺了大模型自己做计算的权力。在 System Prompt 中严格规定：“遇到任何需要计算的数据，绝对不允许直接输出结果，必须写一段 Python 代码来计算。”
  • 我们在后端为 Agent 配备了一个 Python 沙盒（如 Jupyter Kernel 环境）。
  • 当 Agent 遇到财务数据时，它会输出一段类似 result = 3456.78 * 89.12; print(result) 的代码。
  • 后端截获这段代码，送到沙盒里用真实的 CPU 算出来，然后把精确的计算结果作为 Observation（观察）塞回给 Agent。
  • Agent 拿到真实结果后，再用自然语言封装成最终回答输出给用户。

这种‘让语言模型只负责写算式，让 CPU 负责计算’的混合架构，是目前金融、数据分析类 Agent 唯一可靠的落地途径。”

16. 底层前沿理论：上下文窗口扩展机制（Sparse Attention 与 Ring Attention）

面试官提问：“现在的模型动辄支持 100K 甚至 1M 的超长上下文。如果用传统的 Self-Attention，计算复杂度是 $O(N^2)$，1M 上下文早就爆显存了，底层是怎么做到的？”

高阶回答话术与拆解： “要支持超长上下文，业内在底层架构上做了大量的工程与算法创新，突破了 $O(N^2)$ 的物理瓶颈：

  1. Sparse Attention (稀疏注意力)

    • 传统 Attention 是“每个人都要看所有人”。稀疏注意力改为“滑动窗口”（只看附近的 Token）、“全局 Token”（只看特定的开头/总结词）、“随机 Token”。这把计算量降到了 $O(N \log N)$ 甚至 $O(N)$。

  2. Ring Attention (环形注意力)

    • 面对 1M 的上下文，单张 GPU（例如 80GB 显存）无论如何也装不下 KV Cache。Ring Attention 的核心思想是分布式计算。
    • 它把 1M 的长文本切块，分配给集群里的 8 张甚至 64 张 GPU。每张 GPU 计算自己这块的 Q、K、V，然后在 GPU 之间像“击鼓传花（Ring）”一样传递 KV 块。
    • 这样通过多机多卡的 NVLink 高速带宽，绕过了单卡显存的物理限制，实现了真正意义上的“无限长度上下文”。这也是为什么能一次性把整本《红楼梦》甚至一整个代码仓库塞进模型的原因。

  3. RoPE (旋转位置编码) 的外推 (Extrapolation)

    • 模型在预训练时可能只看了 8K 的长度，如何在推理时支持 32K？通过修改 RoPE 的 base 参数（如 YaRN 方法），动态地“挤压”位置编码的空间，让模型在不重新训练的情况下，‘无痛’支持更长的文本。”

17. 陷阱总结：In-Context Learning (上下文学习) vs Fine-Tuning (微调) 决策树

很多候选人一遇到回答不好，就说“我们要去微调（SFT）模型”。这在高级架构师眼里是极度业余的表现。

高阶回答：建立标准的技术决策树：

  • 场景 A：模型不知道某些新知识（比如昨天刚发的新闻，公司内部的机密文档）
    • ❌ 错误做法：微调。微调非常难以让模型记住具体的事实，而且无法实时更新。
    • ✅ 正确做法：RAG（检索增强生成）。把知识存在外部，用的时候去查。
  • 场景 B：模型不懂某种特殊的格式要求（比如必须输出一种你们公司自创的 XML 方言格式）
    • ❌ 错误做法：RAG。
    • ✅ 正确做法：Few-Shot Prompting（少样本上下文学习）。在 Prompt 里直接给它 5 个例子，绝大多数情况下它就能学会。
  • 场景 C：Prompt 里的 Few-Shot 例子太多了，导致 Token 贼贵，而且推理速度极慢，或者它总是学不会你们公司复杂的专有推理逻辑（如复杂的医学诊断流程）
    • ✅ 正确做法：Fine-Tuning (SFT 微调)。微调的本质不是为了“注入知识”，而是为了**“注入能力与格式（Align Capability & Format）”**。通过上万条专有问答对的微调，让模型固化这种推理范式，从而在推理时只需要极其简短的 Prompt 就能输出完美格式，节省 Token 成本并降低延迟。

2025-2026 最新进展

2026 年的理论面试考点正在快速迭代：传统的 Transformer、注意力机制仍是基础门槛，但新增了大量围绕 Agent 范式的考题——ReAct/Plan-and-Execute 的区别、MCP 协议、多 Agent 协作、上下文工程（Context Engineering）、以及 RAG 的进阶形态（GraphRAG、混合检索、重排）。同时面试官越来越关注"你对前沿的跟踪能力"，会问到 DeepSeek-R1、GRPO、长上下文模型等近期热点。

值得注意的趋势是：纯背诵式回答的得分越来越低，面试官更看重你能否结合实践讲清"为什么这么设计、有哪些权衡"。

💡

准备理论题时，每个概念都准备一个"实践锚点"——讲完原理立刻补一句你在项目中怎么用/踩过什么坑。这能瞬间把你和只会背书的候选人区分开。 [!WARNING] 不要忽视前沿动态。2026 年面试中被问到近半年内的新方法（如某个新发布的推理模型或框架）却一无所知，会被直接判定为"不关注行业"，是致命减分项。
