同一项目的两侧重

以智能客服 Agent 为例，这是最常见但也最容易被问出深度的项目。

算法岗表述

面试官想听的是：你的策略选择思路、对比实验、Bad Case 分析以及为什么最终定下这个方案。 他们评估的是你的"研究和优化能力"。

"我对比了三种检索策略：纯向量检索召回率只有 68%，加上 BM25 稀疏检索提升到 74%，再加上 BGE-Reranker 重排序达到 89%。我选择这个方案是因为客服场景对精确关键词匹配要求高（比如用户说'我要退货'，BM25 能精确匹配'退货流程'），而纯语义检索会把'退货'和'换货'搞混。

后来我们发现一个问题，用户有时候问得很简短，比如'年假'。为了解决这个短查询 query 的意图补全，我尝试引入 HyDE (Hypothetical Document Embeddings)。我用一个小模型先生成一段虚构的答案，再去检索。结果发现在某些专有名词上会幻觉，反而带偏检索。所以我最终改成了基于历史会话的 Query Rewrite 策略，用 LLM 结合前 3 轮对话重写当前问题，准确率提升了 12%。"

关键要素：

  • 对比实验（A/B test 思路，不仅要有结果，还要有过程）
  • 策略选择理由（为什么选这个不选那个，甚至要说出踩过的坑）
  • 量化提升（核心指标：Recall, MRR, NDCG 等的变化）
  • Bad Case 驱动优化（遇到什么问题，怎么分析，怎么解决）

开发岗表述

面试官想听的是：你的系统设计思路、性能指标、高可用保障以及复杂状态的管理。 他们评估的是你能不能把这套东西稳定、高效地跑到生产环境。

"我用 LangGraph 搭建了图式工作流，四个节点：意图分类 → 知识检索 → 回答生成 → 转人工判断。架构上，Agent 实例是无状态的，会话存在 Redis 里，向量库用 FAISS 本地部署。上线后单机 QPS 200+，P99 延迟 < 2s。做了 Docker Compose 一键部署，Nginx 负载均衡 + 两个 Agent Worker + Redis + PostgreSQL。

比较有挑战的是流式输出和工具调用的结合。当 LLM 决定调用外部 API（比如查订单）时，我们会暂停流式输出，给前端推一个特定的 status 事件，前端渲染加载动画。API 返回后，再恢复流式文本。为了防超时，所有外部工具调用都加了 3 秒的 timeout 和断路器机制。为了控制成本，我们对相似 Query 做了语义缓存，缓存在 Redis 里的命中率大概在 25% 左右，省了一大笔 token 费。"

关键要素：

  • 系统架构图（能画出来，脑子里有清晰的分层）
  • 技术栈选择理由（为什么用 Redis 做会话存储，为什么用 FAISS 不用 Milvus）
  • 性能指标（QPS/延迟/可用性）
  • 生产环境挑战（超时、流式处理、降级机制、缓存策略）

项目 2：RAG 企业文档问答系统

这个项目非常典型，很多公司的第一个 AI 落地应用就是它。

算法岗版本：策略深挖

markdown 
## 企业文档智能问答系统
2025.10 - 2026.02

- **切分策略优化**：设计文档切分策略对比实验。对比了固定字符大小（500 token）、语义切分（按句号落段）和层级切分（按 Markdown 标题结构）。最终选择了层级切分+滑动窗口策略。在 5000 条企业规章制度文档的测试集上，chunk 的语义完整度提升了 23%，解决了答案被截断导致的幻觉问题。
- **检索架构迭代**：实现 BM25 + FAISS 双路召回，并引入 BGE-Reranker-v2 进行三阶段检索。针对公司特定的缩写词（如"OJT","OKR"），通过构建同义词词典扩展 BM25 词袋。将最终答案的命中率从单路 FAISS 的 68% 提升到 91%，MRR 提升 18%。
- **长下文难题**：针对跨文档的问题，引入多路召回后的合并去重策略。
- **评估体系建设**：摒弃人工肉眼评估，使用 RAGAS 框架搭建了自动化的评估管线。重点监控 faithfulness（忠实度）和 answer_relevancy（相关性）。每两周进行一次 A/B 对比实验，形成了数据驱动的策略迭代闭环。

面试官可能的追问及应对（算法方向）：

  • 问：为什么不用多向量检索（Multi-Vector Retrieval）？
    • 答：考虑过，但多向量检索对文档预处理要求太高，需要用 LLM 针对每个 chunk 生成摘要或假设性问题，这在我们的 10 万+ chunk 规模下成本过高（约 $500），且更新维护慢。我们折中选择了较小的 chunk size + 原文档引用的方式（Parent Document Retrieval）。
  • 问：如何评价 BGE-Reranker 和 Cohere Rerank 的区别？
    • 答：在中文场景下，BGE-M3 的多语言混合效果更好，且支持本地部署。Cohere 虽好但 API 延迟不稳定，且存在数据出境的合规风险。

开发岗版本：架构与性能

markdown 
## 企业文档智能问答系统
2025.10 - 2026.02

- **全链路工作流**：基于 LangGraph 搭建完整的问答工作流，解耦了"文档加载解析"、"向量化"、"检索"和"生成"四个独立微服务。支持 500+ PDF/Word/Markdown 格式文档的并发实时处理，解析成功率 >99%。
- **多级缓存与性能优化**：设计并实现了多级缓存架构。L1 使用本地内存 LRU 缓存热点 Query 的 Embedding 结果；L2 使用 Redis 缓存完整问答对（基于相似度阈值匹配）。在不增加 LLM API 调用的情况下，将系统单机 QPS 从 50 提升到 180，P99 延迟从 3.2s 降至 1.1s。
- **高并发与长连接**：后端使用 FastAPI，针对长文本生成场景实现了 SSE 流式分块输出，并结合 WebSocket 进行长连接会话状态管理，解决 HTTP 超时断开问题。单实例支持 1000+ 并发用户实时问答。
- **工程化交付**：采用 Docker Compose 实现所有依赖（Redis, FAISS server, API）的一键自动化部署。接入 Prometheus 和 Grafana 进行全链路监控，包括大模型 API 的调用延迟、Token 消耗统计和失败率监控。运行 6 个月可用性达到 99.7%。

面试官可能的追问及应对（开发方向）：

  • 问：Redis 缓存相似问答，如果阈值设得太低导致错误回答怎么办？
    • 答：我们加了双重保险。只有当用户的 Query 与 Redis 中缓存的 Query 向量相似度 > 0.95 时才直接返回。且在前端 UI 上，缓存返回的答案会打上"闪电"图标标识为快速回复，引导用户如果不满意点击"重新生成"强制走 LLM。
  • 问：流式输出中断怎么处理？
    • 答：在 FastAPI 端捕获 asyncio.CancelledError，如果是客户端主动断开，我们会立刻停止对 OpenAI API 的流式读取，释放连接资源，防止协程泄漏。

## 自然语言问数 Agent (NL2SQL)
2026.01 - 2026.04

- **Pipeline 设计**：摒弃了简单的端到端生成，设计了"意图识别 → schema 检索 → SQL 生成 → 语法校验（AST层） → 自我纠错（Self-Correction）"的 5 步流程。在内部 200 条复杂业务问数测试集上，SQL 首次执行成功率达 87%。
- **两阶段生成方案**：对比了直接生成 SQL 和两阶段生成（先让 LLM 生成逻辑查询计划，再翻译为特定方言的 SQL）。发现两阶段方案在处理含 3 张表以上的复杂 JOIN 场景时，逻辑清晰度大幅提升，正确率从 62% 提升到 81%。
- **元数据 RAG 增强**：针对字段名歧义（如"收入"是指"GMV"还是"净利润"），搭建了企业级元数据知识库。将表结构、字段说明、业务口径定义及优秀的示例 SQL 向量化。通过 RAG 动态组装 few-shot 提示词，使字段匹配错误率骤降 40%。

开发岗版本：安全与可视化

markdown 
## 自然语言问数 Agent (NL2SQL)
2026.01 - 2026.04

- **系统架构**：基于 LangGraph + MySQL + Qdrant 搭建企业级 NL2SQL 系统。将整个问数流程服务化，提供标准的 REST API 供内部 BI 平台调用。
- **SQL 安全沙箱防护**：为防止 LLM 生成破坏性指令或导致慢查询，在数据库前置了安全拦截中间件。强制解析 AST，只允许 SELECT 操作，禁止 DROP/DELETE/ALTER/UPDATE 等 DDL/DML。对所有合法查询强制追加 LIMIT 100 并在 DB 层面设置 5s 超时断开。
- **前后端全栈联调**：使用 FastAPI 提供接口，前端使用 React + ECharts 实现数据流闭环。除了返回表格数据，Agent 还会根据数据特征自动判断图表类型（折线图、柱状图、饼图）并返回 ECharts 配置项代码，实现前端页面的动态可视化渲染。
- **权限管控**：深度接入公司现有的 SSO (OAuth2) 认证和 RBAC 权限体系。在传递给 LLM 的表结构之前，先进行过滤，确保用户或不同部门只能查询自己有权限的表，实现数据物理隔离。

面试中如何快速"切频道"

面试是一场双人舞，优秀的候选人会根据面试官的反馈调整自己的舞步。同一轮面试中，面试官可能会从算法视角切到工程视角，你要学会无缝切换。

情景演练：开场的"试探"

面试官说："先简单介绍一下你的项目吧。"

此时你不确定他是偏算法还是偏工程？ 采用中性的架构+数据双开场策略，通过抛出"诱饵"看对方咬哪个钩。

"我负责的是一个智能客服 Agent 系统。每天处理 3000+ 用户咨询。核心是用 LangGraph 编排了 4 步工作流。在这个项目中，我主要解决了两个难题：一个是如何把多轮对话中检索的准确率提升到了 90% 以上；另一个是在高并发下如何保证系统的 P99 延迟控制在 2 秒以内。"

说完后停顿观察，或者直接问："您希望我先从业务策略优化的角度讲，还是从系统架构设计的角度展开？"

  • 如果面试官说："讲讲准确率是怎么做到 90% 的。" → 果断切入算法频道，讲你的 3 阶段检索和对比实验。
  • 如果面试官说："讲讲你们 2 秒的延迟是怎么做的，瓶颈在哪？" → 果断切入工程频道，讲你的多级缓存、并发处理和流式输出。

同一个追问，两种截然不同的回答套路

追问："你们的系统如果出错了怎么办？"

分析维度算法岗（偏策略）的回答模式开发岗（偏工程）的回答模式
核心思维分析错误根因 (Root Cause) → 数据回流 → 策略迭代更新故障隔离 (Isolation) → 链路降级 (Fallback) → 快速恢复系统
具体表述"错误主要集中在模糊意图场景。我写脚本提取了日志里的 200 条 bad case 进行人工标注，发现 60% 是因为大模型在意图分类阶段把闲聊当成了业务咨询。于是我优化了 System Prompt，加入了 Few-shot 样例，并且加了意图分类的前置独立节点，准确率回升了 15%。""我们在架构上设计了三级降级策略。第一级：如果 LLM API 超时（超过 5s），立刻中断并走本地 Redis 的兜底缓存；第二级：如果 RAG 检索服务挂了，让大模型基于自身知识做泛化回答并提示风险；第三级：全部失效时自动跳转人工客服。所有异常都会触发 Prometheus 告警并推送到飞书群，我们要求 5 分钟内响应。"
考察的关键词Bad Case 分析、数据飞轮、Prompt 优化、Few-shot降级机制 (Graceful Degradation)、高可用 (HA)、SLA、监控告警

场景 3：为什么选这个技术？

追问："为什么用 BGE-M3 作为 Embedding 模型而不用 OpenAI 的 API？"

算法视角的回答（强调效果与评测）：

"我们在初期做了选型评估。参考了 MTEB 中文 benchmark，并在我们的业务数据集上跑了对比。发现 BGE-M3 在中文特定领域词汇上的召回率比 text-embedding-ada-002 高 3.5 个百分点。并且 BGE-M3 支持稠密检索、稀疏检索和多向量检索机制，为我们后续的策略升级留了空间。加上开源可本地部署，避免了敏感数据的外传风险。"

工程视角的回答（强调性能与成本）：

"主要是出于延迟和成本的综合考量。我们的 SLA 要求 P99 延迟 < 100ms。实测发现 OpenAI API 跨国网络延迟波动很大（经常在 50-300ms 之间跳动），而 BGE-M3 使用 ONNX Runtime 本地部署在 GPU 机器上，延迟稳定在 15-20ms 左右。另外，我们一天有几十万次的 Embedding 调用，如果用 OpenAI 每个月成本要几千块，而本地化部署后除了一台 T4 服务器的成本，边际调用成本几乎为零。"

算法岗 vs 开发岗：到底差在哪（量化对照）

很多人嘴上说"双轨"，心里却分不清两个岗位真正考的是什么。下表把两条赛道的核心差异拉平对比，照着补短板。

对比维度算法岗 (AI 算法/研究)开发岗 (AI 应用/全栈)
核心命题"为什么这样做效果更好""怎么让它稳定高效跑起来"
高频考点RAG 策略、评估指标、微调、Bad Case 分析架构设计、高并发、缓存、降级、可观测
量化语言Recall/MRR/NDCG/faithfulnessQPS/P99/可用性/Token 成本
手撕题倾向评估脚本、检索融合、采样策略并发工具调用、限流熔断、状态机
加分项读过论文、做过对比实验、有数据飞轮扛过线上事故、做过容量规划、懂成本
致命减分"调包侠"、说不清为什么选这个方案"Demo 工程师"、没上过真实生产
典型职级薪资带(1-3年)25K~45K (算法稀缺溢价)22K~40K (工程供给略多)
💡

双轨不是两边都学一半，而是同一个项目准备两套叙事。技术深度靠主轨，辅轨只需能接住基础追问。

双轨自评：你该主攻哪条赛道

转岗/双轨最忌"平均用力"。下面这个脚本帮你用打分量化自己的赛道适配度，明确主轨与辅轨。

python 
"""
dual_track_advisor.py —— 双轨主辅赛道自评
按真实能力打分(0~5)，输出主轨建议与辅轨补强清单。
"""
from dataclasses import dataclass, field

@dataclass
class SkillProfile:
    # 算法侧能力 (0~5)
    paper_reading: int      # 论文阅读/前沿跟踪
    eval_methodology: int   # 评估方法论(RAGAS/AB实验)
    retrieval_tuning: int   # 检索策略调优
    finetune: int           # 微调/数据构造
    # 工程侧能力 (0~5)
    system_design: int      # 系统架构设计
    high_concurrency: int   # 高并发/性能优化
    devops: int             # 部署/监控/CICD
    incident: int           # 线上排障/容量规划

def advise(p: SkillProfile) -> dict:
    algo = p.paper_reading + p.eval_methodology + p.retrieval_tuning + p.finetune
    eng = p.system_design + p.high_concurrency + p.devops + p.incident
    main = "算法岗" if algo > eng else "开发岗"
    gap = abs(algo - eng)
    # 找出辅轨最弱的两项，作为重点补强
    eng_items = {"系统架构": p.system_design, "高并发": p.high_concurrency,
                 "部署运维": p.devops, "线上排障": p.incident}
    algo_items = {"论文跟踪": p.paper_reading, "评估方法": p.eval_methodology,
                  "检索调优": p.retrieval_tuning, "微调": p.finetune}
    weak = sorted((eng_items if main == "算法岗" else algo_items).items(),
                  key=lambda x: x[1])[:2]
    return {
        "算法分": algo, "工程分": eng, "主轨建议": main,
        "差距": gap,
        "策略": "差距大,主轨打深辅轨保底" if gap >= 5 else "双轨均衡,均可冲击",
        "辅轨重点补强": [k for k, _ in weak],
    }

if __name__ == "__main__":
    me = SkillProfile(paper_reading=2, eval_methodology=3, retrieval_tuning=3,
                      finetune=1, system_design=4, high_concurrency=4,
                      devops=4, incident=3)
    import json
    print(json.dumps(advise(me), ensure_ascii=False, indent=2))
    # 典型后端背景输出：主轨=开发岗，辅轨重点补"论文跟踪/微调"

面试现场：如何 30 秒锁定面试官的"频道"

flowchart TD
    Open[中性双开场<br/>抛架构+数据双诱饵] --> Listen{面试官追问方向?}
    Listen -->|"准确率怎么做到的"| Algo[切算法频道]
    Listen -->|"延迟/并发怎么扛的"| Eng[切工程频道]
    Listen -->|"先讲讲整体设计"| Probe[反问:从策略还是架构展开?]

    Probe --> Listen
    Algo --> A1[3阶段检索+对比实验<br/>Bad Case驱动优化<br/>评估指标量化]
    Eng --> E1[多级缓存+流式输出<br/>降级熔断<br/>QPS/P99数据]

    A1 --> Watch{对方是否点头/追更深?}
    E1 --> Watch
    Watch -->|深挖本频道| Stay[继续加深, 这就是对的轨]
    Watch -->|转问另一面| Switch[平滑切轨<br/>用同一项目另一侧叙事]
    style Stay fill:#dcfce7,stroke:#16a34a
    style Switch fill:#dbeafe,stroke:#2563eb
⚠️

切轨要"平滑"而非"翻脸"。从算法切到工程时说"这套策略要稳定跑到生产，我在工程上做了三件事…"，让面试官感觉你是一个完整的人，而不是背了两套话术。

真实案例：一个后端用双轨拿下算法岗 offer

背景：候选人 L，Java 后端 3 年，自学 Agent 4 个月。本想只投开发岗，听从双轨建议同时准备算法叙事。

阶段事件双轨策略发挥的作用
投递投了某中厂"算法工程师(Agent方向)"JD 偏算法，L 切换为算法简历版本
一面面试官追问"检索召回率怎么提的"L 用准备好的算法叙事：BM25+向量+Rerank 三阶段，附 MRR 提升数据
二面转问"这套怎么扛 200 QPS"L 切工程频道：多级缓存+语义缓存命中率 25%，面试官惊喜
三面(总监)"你到底算法强还是工程强"L 答"工程是我的根，算法是我的刃"，主辅清晰不含糊
结果拿到算法岗 offer，比纯开发岗高 8%双能力让 L 在"边界模糊"的岗位上脱颖而出

复盘：L 的工程是主轨（讲得最深最稳），算法是辅轨（能接住追问且有数据支撑）。正是二面那段"工程频道"的从容，让总监认定他是"既懂模型又能落地"的稀缺复合型人才。

双轨策略的底层逻辑（心法）

很多人对"双轨"有误解，以为是要你成为百年难遇的"全栈天才"。

不，你不需要真的同时精通顶尖算法和极致的底层工程。

你只需要做到：

  1. 一个非常扎实的项目底座：这个项目必须有策略思考的痕迹（算法面所需），也有严谨的代码落地实现（工程面所需）。
  2. 两套流利的表述剧本：把同一件事情，从"研究型问题"和"工程型问题"两个视角讲透彻。
  3. 一个清晰的自我认知：心里很清楚自己到底更擅长哪一端。把擅长的那一端作为"保底必杀技"，把另一端作为"惊艳加分项"。

核心心法总结：投算法的时候，把项目包装成"研究型落地"（我有理论，且我能让理论跑起来）；投开发的时候，把项目包装成"工程型架构"（我能搭高并发系统，且我懂 LLM 的底层脾气）。

面试的本质不是展示你的全部，而是让面试官看到他极度渴望看到的那一面。 准备好你的两套面具，随时上场。

2025-2026 最新进展

双轨策略在 2026 年的岗位错配市场中价值进一步凸显。由于企业对 Agent 岗的定位普遍模糊（既想要懂模型评估/微调的算法人，又想要能扛高并发/工程化落地的开发人），同时具备两侧能力并能按岗位灵活切换叙事的候选人，命中率明显高于单一定位者。实践中的关键是"一项目两版本"——同一个 Agent 项目，面算法岗时强调评估指标、提示优化、模型选型；面开发岗时强调架构、并发、成本与可观测。

需要清醒认识的是：双轨不等于两边都浅尝辄止。市场最终淘汰的是"什么都会一点、什么都不深"的人。

💡

双轨准备时设定一个"主轨 + 辅轨"：把 70% 精力投入你最擅长的方向做到面试官挑不出毛病，剩余 30% 保证辅轨能接住基础追问即可，避免平均用力导致两边都不过关。 [!WARNING] 切忌在同一场面试中频繁切换人设。一旦面算法岗就坚定走算法叙事，中途暴露工程短板时硬拗算法反而失分。投递前就确定本场主打哪一轨。
